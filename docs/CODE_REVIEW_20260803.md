## ① 페이지 코드가 전부 초기 번들에 들어감 (성능)

**사실**

`App.jsx` 는 13개 페이지 컴포넌트를 전부 정적 `import` 합니다. 동적 `import()` 나 `React.lazy()` 사용은 **0건**입니다.

결과적으로 `main-*.js` 가 **504KB** 이고, 랜딩만 보는 방문자도 전부 내려받습니다.

정적으로 묶이는 페이지 소스 크기:

| 컴포넌트 | 크기 | 랜딩 방문자에게 필요한가 |
| :--- | ---: | :--- |
| `AnalysisPage` | 76K | 아니오 |
| `pages/BuyerSearch` | 72K | 아니오 |
| `ExportFlowPage` | 64K | 아니오 |
| `AdminDashboard` | 36K | **아니오 — 관리자 전용** |
| `PricingPage` | 20K | 아니오 |
| `LandingPage` | 16K | 예 |
| 나머지 7개 | 68K | 아니오 |

첫 화면에 필요한 건 `LandingPage` 16K 뿐인데 364K 를 받습니다. 특히 `AdminDashboard` 는 관리자만 쓰는 화면인데 모든 방문자에게 전송됩니다.

**참고** — `jspdf`(348K), `html2canvas`(200K) 는 이미 별도 청크로 분리돼 있습니다. 페이지 컴포넌트만 안 되어 있습니다.

**제안**

`App.jsx` 의 라우트 컴포넌트를 `React.lazy()` + `<Suspense>` 로 바꿉니다.

```jsx
const AdminDashboard = lazy(() => import('./AdminDashboard'))
const AnalysisPage   = lazy(() => import('./AnalysisPage'))
// …
```

**위험**: 화면 전환 시 청크를 새로 받으므로 첫 진입에 짧은 지연이 생깁니다. `<Suspense fallback>` 처리가 필요하고, 기존 화면 전환 E2E 가 이 지연을 견디는지 확인해야 합니다.

**측정 없이 수치를 약속하지 않습니다.** 실제 감소폭은 적용 후 재보면 됩니다.

## 확인했고 문제 없던 것

### 백엔드 인가 — 38개 엔드포인트

`main.py` 13개 + 라우터 25개를 전수 확인했습니다.

인증 없이 열린 것은 의도된 4개뿐입니다.

- `GET /v1/health` — 상태 확인
- `GET /v1/demo/snapshot`, `/v1/demo/summary`, `/v1/demo/buyers` — 로그인 화면 통계 등 공개 데모

권한 계층도 맞습니다.

- 크레딧 **충전**(`/v1/credits/charge`) → `require_admin`
- 크레딧 **차감**(`/v1/credits/deduct`) → `get_current_user`
- 인콰이어리 관리(`/admin/inquiries/*`) 7개 → 전부 `require_admin`
- 인콰이어리 생성(`POST /v1/inquiry`) → `require_plan("Advanced")`

`GET /v1/admin/p2-status` 만 의존성 대신 본문에서 `role != "admin"` → 403 을 던집니다. 동작은 같지만 다른 관리자 엔드포인트와 방식이 달라, 나중에 읽는 사람이 보호 여부를 오해할 여지는 있습니다. 기능 문제는 아닙니다.

### 결제 웹훅

`POST /v1/payment/webhook` 은 인증이 없는 게 맞습니다(외부 호출). 대신 `verify_webhook_signature` 로 HMAC 을 검증하고, **시크릿 미설정 시 전량 거부(fail-closed)** 합니다.

주석에 실제 토스 서명 스킴이 다를 가능성과 라이브 전 확인 조건까지 적혀 있습니다(L018). 추측으로 통과시키지 않은 판단이 적절합니다.

### E2E 정리 엔드포인트

`POST /v1/e2e/cleanup` 은 사용자를 삭제하는데, 방어가 4중입니다.

1. `APP_ENV=e2e` 일 때만 라우터를 마운트 (`main.py:35`)
2. 핸들러 내부에서 환경 재확인 → 아니면 404
3. `X-E2E-Admin-Token` 헤더가 `E2E_ADMIN_TOKEN` 과 일치해야 함 (미설정 시 503)
4. 이메일이 `^e2e-[a-z0-9-]+@example\.com$` 형식이어야 함 → **실제 사용자는 삭제 불가**

- `dangerouslySetInnerHTML`, `innerHTML =`, `eval(`, `new Function(`: 사용처 없음

## 점검 방법의 한계

- **정적 분석 위주**입니다. 실행 중에만 드러나는 경쟁 상태나 데이터 정합성 문제는 이 방식으로 잡히지 않습니다.
- 인가 확인은 **엔드포인트 진입점** 기준입니다. 핸들러 안에서 다른 사용자의 자원에 접근하는지(IDOR)는 개별 검토가 필요합니다.
- 프론트엔드는 XSS 패턴과 번들만 봤고, 상태 관리나 접근성은 범위 밖입니다.
- 초안에서 `POST /v1/credits/charge` 등이 무인증으로 잡혔으나, 여러 줄 함수 시그니처를 놓친 정규식 오류였습니다. 전수 재확인 후 정정했습니다.
