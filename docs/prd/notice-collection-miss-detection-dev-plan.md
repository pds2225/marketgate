# 공고 자동수집·추천 — 누락 탐지 중심 개발계획서 (보완본)

| 항목 | 내용 |
|---|---|
| 문서 상태 | **세션 합의 반영 / 구현 미착수** |
| 작성 기준일 | 2026-07-25 |
| 범위 | 공고 파이프라인(수집→추출→판정→기업매칭→요약→발송) |
| 핵심 원칙 | **수집·추출 = P0 / 판정·추천·요약 = P1** |
| 관련 교훈 | L006(상태 라벨), L007(문제≠WBS) |

---

## 0. 한 줄 결론

기능 부족보다 **누락 유형·단계·우선순위가 분리되지 않은 것**이 핵심 위험이다.  
P0는 「공고가 시스템에 들어오지 않거나, 들어온 뒤 필수 정보가 깨진 채 조용히 통과하는 것」만 담당하고, 추천·요약 품질은 P1로 분리한다.

---

## 1. 문제 정의 (확정)

서비스의 최대 운영 위험은 **실제 존재하는 공고가 사용자에게 전달되지 않는 것**이다.

| 구분 | 발생 지점 | 대표 문제 | 우선순위 |
|---|---|---|---|
| 원천 수집 누락 | 사이트 접속·목록 수집 | 미실행, 파서 실패, 페이지 누락, 건수 급감 | **P0-A** |
| 정보 추출 누락 | 상세페이지 보강 | 마감일·지역·대상 미추출 / 미기재와 실패 혼동 | **P0-B** |
| 판정 누락 | 그룹·기업 적합성 | 키워드·지역·유형 오판 | **P1-A** |
| 전달 누락 | 요약·메일 | 요약 실패로 제외, 그룹·기업별 미표시 | **P1-C** (+ Delivery 추적) |

**본질:** 프로그램이 오류 없이 종료된 것과, 공고를 빠짐없이 수집·추출한 것은 다르다.

## 2. 현재 요청의 구조적 결함 (검토 결과)

### 2.1 P0 범위 과대 — 완료조건·중단기준 불명확

④ 상세정확도 · ⑤ 키워드/지역 판정 · ⑧ 기업추천 · ⑨ Claude 요약을 모두 P0로 묶으면:

- 어떤 실패에서 운영을 중단해야 하는지 불명확
- 개발 공수가 추천·표현으로 분산됨
- 테스트 합격 기준이 「수집 재현율」과 「요약 문장 품질」로 섞임

**보완 방침:** P0 완료 = 단계별 누락 탐지·알림·재수집이 동작하는 것. P1은 별도 완료조건.

### 2.2 단계 상태 부재 — 사고 시 원인 분석 불가

필수 파이프라인 상태(저장 단위: 실행 run_id + source_id + notice_id):

| 단계 | 저장 상태 (권장 enum) | P0/P1 |
|---|---|---|
| Fetch | `SUCCESS` / `PARTIAL` / `FAILED` / `SKIPPED` | P0 |
| Enrich | `COMPLETE` / `PARTIAL` / `FAILED` / `SKIPPED` | P0 |
| Normalize | 필드별 `OK` / `NOT_SPECIFIED` / `PARSE_FAILED` | P0 |
| Evaluate | `INCLUDE` / `REVIEW` / `EXCLUDE` + reason_codes[] | P1 (저장은 P0부터) |
| CompanyMatch | 기업별 score, promote_flag, hard_exclude | P1 |
| Summarize | `OK` / `FALLBACK_TEMPLATE` / `FAILED` | P1 |
| Delivery | 메일 포함 여부, 그룹/기업 슬롯 | P1 (추적 스키마는 P0) |

> **상태 라벨:** Evaluate~Delivery의 **저장 스키마는 P0에서 골격만** 만들고, **품질 개선 로직은 P1**. (가정 → 구현 시 ADR로 확정)

### 2.3 「0건」 모호성 · 기준선 오염 · 사이트 이질성

동시에 해결하지 않으면 오경보 또는 미탐이 발생한다. → §5 예상문제 E01~E04.

## 3. 우선순위 확정 (개발 게이트)

### P0-A. 원천 수집 누락 탐지 — **운영 중단/재수집 트리거**

| ID | 작업 | 완료조건 |
|---|---|---|
| A1 | 활성 소스 실행대장(registry) | 활성 site 100%가 매 run에 상태 기록 |
| A2 | 소스별 SUCCESS/PARTIAL/FAILED | 미실행 = FAILED(미실행)로 명시 |
| A3 | 수집건수 급감 탐지 | 사이트별 threshold, SUCCESS run만 기준선 |
| A4 | 0건 이상탐지 | zero_item_policy: `p0` / `warning` / `ignore` |
| A5 | 페이지네이션 누락 | expected_pages vs fetched_pages |
| A6 | 파서·목록 구조 실패 | 링크 추출률, 본문 해시·점검페이지 탐지 |
| A7 | 누락 기간 재수집 | P0 발생 시 lookback 재조회 + 재시도 정책 |

### P0-B. 정보 추출 누락 탐지 — **판정 전제조건**

| ID | 작업 | 완료조건 |
|---|---|---|
| B1 | 필수필드 계층화 | 절대필수 / 판정필수 / 선택 (§4.2) |
| B2 | 미기재 vs 파싱실패 분리 | `NOT_SPECIFIED` ≠ `PARSE_FAILED` ≠ `DETAIL_FETCH_FAILED` |
| B3 | 필드 추출률 모니터링 | 사이트별 판정필수 필드 추출률 ≥ KPI |
| B4 | Enrich 실패 공고 | 자동 EXCLUDE 금지, `REVIEW` 유지 |

### P1-A. 판정 오판 방지

키워드 구역 분리, Hard Exclusion, 판정근거 저장, Golden Set.

### P1-B. 기업 추천 고도화

그룹 탈락 재검토, 적합점수·승격·상한, Hard Exclusion 우선.

### P1-C. Claude 요약 안정화

사실 = 구조화 데이터 출력, Claude = 적합사유·확인사항만, 실패 시 템플릿, **요약 실패로 공고 제외 금지**.

## 4. 설계 보완 사항 (반드시 선반영)

### 4.1 실행 상태 vs 소스 상태 분리 (발송 충돌 해소)

| 레벨 | 상태 | 의미 | 발송 |
|---|---|---|---|
| Source | SUCCESS / DEGRADED / FAILED | 개별 사이트 | 해당 소스만 영향 |
| Run | SUCCESS / DEGRADED / FAILED | 전체 실행 | DEGRADED=정상 소스만 발송, FAILED=발송 보류 |

**규칙:** 개별 소스 P0 ≠ 전체 run P0. 「발송 계속」은 Run=DEGRADED일 때만 허용.

### 4.2 필수필드 계층

| 구분 | 항목 |
|---|---|
| 절대 필수 | 공고명, 기관, 원문 URL |
| 판정 필수 | 접수상태, 지원대상, (지역 **또는** 지역미지정 플래그) |
| 선택 | 지원금액, 신청방법, 세부 일정 |

지원금액 “기업별 상이”, 전국(문구 없음), 첨부파일만 신청방법, 상시접수(마감일 없음)은 **실패가 아니라 NOT_SPECIFIED 가능**.

### 4.3 필드 상태 모델

```text
NOT_SPECIFIED        # 원문에 해당 정보 없음(확인됨 또는 휴리스틱)
PARSE_FAILED         # 원문 존재 가능성 있으나 추출 실패
DETAIL_FETCH_FAILED  # 상세 URL 접근 실패
OK                   # 정상 추출
```

`region_unknown` 단일 코드 폐기(또는 deprecated). UI/메일은 상태 코드를 사람이 읽는 라벨로 매핑.

### 4.4 사이트별 탐지 설정 (동일 기준 금지)

```json
{
  "site_id": "incheon_tp",
  "zero_item_policy": "warning",
  "drop_threshold": 0.8,
  "minimum_baseline": 5,
  "expected_frequency": "weekly",
  "pagination_required": true,
  "baseline_window": 7,
  "baseline_only_success": true
}
```

| 사이트 유형 | 권장 zero_item_policy | drop_threshold |
|---|---|---|
| 대형 통합포털 | `p0` | 0.7~0.8 |
| 지역기관 | `warning` | 0.8 + minimum_baseline |
| 월간 공고 | `ignore` 또는 주기 윈도우 | 낮게 또는 비활성 |
| API 기관 | `p0`(스키마/필드) | 필드 누락률 중심 |
| HTML 기관 | `p0`(구조·추출률) | 구조 인식 실패 즉시 |

### 4.5 기준선 오염 방지

- **SUCCESS로 검증된 실행만** 기준선 반영
- P0/P1(이상) 실행은 기준선 **제외**
- 최근 정상 중앙값 + 장기(예: 30회 SUCCESS) 평균 **동시** 비교
- `human_verified_ok` 플래그 있으면 가중 반영(선택)

### 4.6 탐지 후 후속조치 (탐지 ≠ 복구)

| 단계 | 기본값(가정, 구현 전 확정) |
|---|---|
| 자동 재시도 | 최대 3회 |
| 재시도 간격 | 5m → 15m → 60m (backoff) |
| 재시도 성공 | 해당 소스 P0 자동 해제, run은 DEGRADED→재평가 |
| 수동확인 큐 | 재시도 실패 시 티켓 생성(site_id, 기간, 증거 스냅샷) |
| 재수집 범위 | last_success_at ~ now (+ overlap 1일) |
| 관리자 확인 | `ack` / `false_positive` / `fixed` — false_positive는 설정 튜닝 후보 |

### 4.7 그룹 vs 기업 역할 분리 (P1)

| 구분 | 역할 |
|---|---|
| 그룹 판정 | 주제·지원유형·기본 지역 |
| 기업 판정 | 업력·매출·기술·관심분야 |
| 사용자 선호 | 받고 싶은 유형 |
| 제외규칙 | 공급기업전용·마감종료 등 Hard Exclusion |

기업 승격 가드: 키워드 중요도, 필수/선택 구분, 최소 점수, 정량조건, Hard Exclusion 우선, **기업당 일일 추천 상한**.

### 4.8 Claude 범위 제한 (P1, P0에 포함 금지)

- 요약 실패 → 공고 EXCLUDE 금지
- FALLBACK_TEMPLATE로 발송 가능해야 함
- 사실정보(마감·기관·URL·금액)는 DB 필드에서만 출력

## 6. 목표 KPI (초기 운영 가정 — 검증필요)

| KPI | 목표 | 측정 위치 |
|---|---|---|
| 활성 소스 실행률 | 100% | Fetch 대장 |
| 명백한 신규공고 수집 재현율 | ≥ 98% | Golden 목록 대비 |
| 판정필수 필드 추출률 | ≥ 95% | Enrich/Normalize |
| 명백 적합공고 누락률 | ≤ 3% | Evaluate+Delivery |
| review 비율 | ≤ 20% 후보 | Evaluate |
| 중복공고율 | ≤ 2% | Normalize/dedupe |
| 관리자 오경보율 | ≤ 15% | P0 ack=false_positive |

정확도(오탐↓)와 재현율(누락↓)은 트레이드오프이므로 **단일 KPI로 완료 판정하지 않는다**.

## 8. 테스트·완료 게이트

### P0 Done 정의

1. 활성 소스 미실행이 P0로 잡힌다.
2. SUCCESS-only 기준선으로 급감/0건이 사이트 정책대로 동작한다.
3. Soft-fail(점검/로그인 페이지)이 SUCCESS로 기록되지 않는다.
4. Enrich/Parse 실패가 NOT_SPECIFIED와 구분되어 저장된다.
5. 개별 소스 FAILED여도 타 소스 공고는 Run=DEGRADED로 발송 가능하다.
6. P0 후 자동 재시도·lookback·수동큐가 문서화된 대로 돈다.
7. Claude/기업추천 코드 변경 **없이도** 위 1~6이 만족된다. (범위 오염 방지)

### P1 Done 정의 (요약)

- Golden Set 회귀 통과, 기업 상한·Hard Exclusion 동작, 요약 실패 시에도 Delivery 가능.

### 회귀 테스트 최소 세트

| 테스트 | 기대 |
|---|---|
| 활성 소스 1개 스킵 | P0 + 미실행 사유 |
| 평소 30건 → 2건 | P0 (threshold·baseline 충족 시) |
| 0건 + zero_item=warning | 경고만, 발송 계속 |
| 상세 404 | DETAIL_FETCH_FAILED, REVIEW |
| 전국·지역문구 없음 | region=NOT_SPECIFIED (실패 아님) |
| Claude timeout | FALLBACK_TEMPLATE, 메일 포함 |

## 11. 개발 순서 (실행 체크리스트)

```text
[ ] W0 스키마·config·Golden Set 합의
[ ] P0-A 탐지·알림·재시도·발송 게이트
[ ] P0-B 필드 상태·추출률·REVIEW 유지
[ ] P0 완료게이트 §8 통과 → 운영 전환
[ ] P1-A 판정
[ ] P1-B 기업 추천
[ ] P1-C Claude/Delivery 안정화
[ ] KPI 2주 관측 후 threshold 재조정 (검증필요)
```

## 12. 종합

현재 개발요청의 방향은 타당하나, **수집 누락 탐지와 추천·요약 품질이 한 P0에 혼합**되어 있다.  
개발의 중심은 크롤러 추가가 아니라:

**활성 사이트 실행 검증 → 원천 수집 검증 → 상세 추출 검증 → (상태 저장) 판정·기업·요약·발송 추적**

④·⑤·⑧·⑨는 유지하되 **수집·추출=P0, 판정·기업·Claude=P1**으로 완료조건과 테스트를 분리한다.

## 부록 A. 상태 라벨 범례 (L006)

| 라벨 | 의미 |
|---|---|
| 문서 확정 | 본 문서에 합의된 개발 계약 |
| 세션 합의(미반영) | 코드/ADR 미반영 |
| 가정 | 재시도 횟수·KPI 수치 등 — 운영 데이터로 재검증 |
| 검증필요 | Golden Set·임계값 실측 후 확정 |

본 문서 본문은 **문서 확정(우선순위·단계분리·필드계층)** + **가정/검증필요(수치·재시도 파라미터)**가 혼재한다. 구현 착수 전 W0에서 가정을 ADR로 승격할 것.
